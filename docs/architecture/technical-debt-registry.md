# TechForge Core — Technical Debt Registry

> Consolida achados não corrigidos das revisões de arquitetura em
> `docs/architecture/*.md` mais os gaps reais remanescentes descritos em
> [`docs/limitations.md`](../limitations.md) que não dependem de
> infraestrutura ainda inexistente (instalador Windows, servidor
> central). Registrar
> dívida não é escondê-la nem resolvê-la às cegas — é torná-la visível
> pra decisão futura.

| ID | Área | Descrição | Impacto | Prioridade | Motivo do adiamento | Quando revisitar |
|---|---|---|---|---|---|---|
| TD-001 | Package Manager | `package_manager/lifecycle.py` importa `app.main` dentro de `activate_module()` pra montar router sem reiniciar o processo (hot activation) — inversão de camada (Core Service → bootstrap) | Baixo — import deferido, sem erro de boot | Baixa | Não há solução mais barata sem introduzir um padrão de registro de router mais indireto; funcionalmente necessário hoje | Se o padrão de hot activation for revisado por outro motivo |
| TD-002 | API routes | `api/routes/security.py` importa `list_modules_trust` de `api/routes/module_verification.py` — rota reaproveitando handler de outra rota como serviço | Baixo — funciona, mas mistura camada de transporte com lógica compartilhada | Baixa | Extração envolve estado mutável (`_last_known_trust`) e publish de eventos — risco maior que uma simples movimentação de código | Se `security.py` ou `module_verification.py` precisarem de mudança por outro motivo |
| TD-003 | Runtime | Dois enums distintos chamados `RuntimeState` (`app/runtime/__init__.py` = estado da plataforma; `app/module_runtime/state.py` = estado de execução de módulo) — colisão de nome | Baixo — nomenclatura, não comportamento | Baixa | Mesmo padrão já aceito pra `runtime_id`/`execution_id`; renomear quebraria callers/testes existentes sem ganho funcional | Só se causar confusão real reportada por quem lê o código |
| TD-004 | Module lifecycle | Lifecycle de módulo fatiado em 3 enums (Package job / Administrative / Runtime) com nomes divergentes do exemplo de 7 estados documentado na spec de arquitetura (`INACTIVE` vs `DISABLED`, sem `ACTIVE` dedicado) | Baixo — comportamento correto, só nomenclatura | Baixa | Unificar os 3 enums é uma reescrita de um componente estável sem necessidade funcional real | Se um módulo real expuser confusão prática entre os estados |
| TD-005 | Package Manager / Trust | `SecurityPolicy.allows_install()`/`requires_warning()` estão implementados e documentados, mas nunca são chamados em `install()` nem `update()` — o "aviso de trust" na instalação nunca chega ao usuário | Médio — funcionalidade de segurança pronta mas desconectada; decisão de não bloquear é intencional, o aviso não | Média | Requer decisão de UX (onde/como exibir o aviso — campo na resposta de install? banner na UI?), não é fix mecânico | Antes de expor instalação remota a um público mais amplo que o single-user atual |
| TD-006 | Example modules | `system_information_service/frontend/index.tsx` tem o mesmo problema que o `hello_world` tinha (`.tsx` não servível pelo allowlist de assets) | Baixo — UI do módulo é mínima (`return null`), não afeta funcionalidade real | Baixa | Fora do escopo explícito da correção do `hello_world`; sem urgência dado que o módulo não tem UI de fato | Se esse módulo ganhar uma UI real |
| TD-007 | Observability | `_persist_execution_history()` pula a gravação silenciosamente se chamado de dentro de um event loop já rodando — funciona hoje porque o único call site de `invoke()` é síncrono (roda em threadpool), mas é frágil a um futuro call site `async def` | Baixo hoje, Médio se crescer | Baixa | Não há call site problemático ainda — corrigir preventivamente seria especulativo | Antes de adicionar qualquer novo caminho de execução de módulo que seja `async def` |
| TD-008 | Package Manager | `InstallJobRegistry._jobs` é um dict in-memory amarrado ao processo que criou o job — não sobrevive a múltiplos workers | Baixo no cenário atual (Desktop single-process) | Baixa | Fora de escopo enquanto a plataforma for single-process por design | Só se/quando houver decisão de rodar múltiplos workers |
| TD-009 | Observability | `StorageProvider.health_check()` só tem cobertura de teste pro caminho saudável — nenhum teste cobre disco cheio/indisponível | Médio — lacuna de confiança no health check que alimenta diagnósticos | Média | Não é um bug conhecido, é ausência de teste — adicionar exigiria simular falha de storage de forma confiável no ambiente de teste | Ao revisar a suíte de testes de resiliência |
| TD-010 | Testes | Suíte completa do backend apresenta 2 falhas dependentes de ordem de execução (`test_unread_only_filter`, `test_snapshot_computes_failure_rate`) que passam isoladamente — indica vazamento de estado entre arquivos de teste, não bug de produto | Médio — mina a confiança em "suíte verde" como sinal, exige triagem manual quando falha | Média | Root cause (qual fixture/estado global vaza) não investigado a fundo nesta revisão | Na próxima vez que a suíte falhar de forma inesperada, investigar antes de assumir flakiness |
| TD-011 | Module Runtime | Hot-unload de módulo não implementado — desativar um módulo não descarrega o que já está montado em runtime, exige restart da plataforma | Médio — usabilidade, não corretude | Média | Citado como candidato desde os componentes iniciais de execução de módulo, nunca priorizado por falta de módulo real que dependesse disso | Quando um módulo real precisar de desativação sem restart |
| TD-012 | CLI | `cli/techforge_cli/validators/module_validator.py` duplica parte da validação de compliance de documentação que já existe no `doc_engine` (`DocCompletenessChecker`) | Baixo — duplicação de lógica, não bug funcional | Baixa | Consolidar exigiria confirmar que as duas validações realmente checam a mesma coisa, ponto a ponto | Ao mexer em qualquer um dos dois validadores por outro motivo |
| TD-013 | Service Registry | Conflito de capability entre providers concorrentes é reportado, mas não há política de precedência pra resolvê-lo automaticamente | Médio — só vira problema real com 2+ módulos oferecendo a mesma capability | Média | Sem caso real de conflito em produção ainda pra guiar qual política faz sentido | Quando dois módulos reais declararem a mesma capability |
| TD-014 | Module Runtime | Estado `BLOCKED`/Runtime State de um módulo não é recalculado automaticamente no boot quando uma dependência fica insatisfeita com a plataforma desligada — só reavaliado em `activate`/`initialize` explícito | Baixo — exige uma sequência específica de eventos (dependência removida enquanto a plataforma está fechada) | Baixa | Recalcular todo o grafo de dependência no boot tem custo, e o caso é raro | Se esse cenário específico causar confusão real reportada |
| TD-015 | Marketplace | Não há como instalar ou consultar uma versão antiga específica de um módulo — o armazenamento já preserva todo `.mod` publicado, mas nada expõe isso além da versão mais recente do índice | Baixo — feature ausente, não bug | Baixa | Sem caso de uso real que precisasse de rollback de módulo até agora | Se um módulo real precisar de rollback de versão |
| TD-016 | Package Manager | `RemoteRepositoryProvider` continua stub (`NotImplementedError`) — funcionalidade equivalente já entregue por outro caminho (`CatalogAggregator`/`CustomCatalogProvider`), classe ficou órfã | Baixo — código morto, sem uso real | Baixa | Remoção seria trivial, mas não foi confirmada com o mesmo rigor das demais revisões desta consolidação | Na próxima limpeza de código morto do Package Manager |
| TD-017 | Security | Secret Store (`keyring`) sem fallback para SO sem backend compatível (Linux headless sem D-Bus/Secret Service) | Baixo no cenário atual (Desktop Windows) | Baixa | Só relevante se houver deploy Linux sem sessão gráfica, não é o alvo atual | Antes de qualquer suporte oficial a Linux headless |
| TD-018 | Frontend | UI nunca verificada visualmente em navegador real por ferramenta de automação — `npm run build` cobre compilação, não comportamento visual | Médio — lacuna de confiança em regressões visuais | Média | Sem ferramenta de browser automation disponível de forma consistente nas sessões de trabalho até agora | Ao configurar testes visuais/E2E de frontend |
| TD-019 | CLI | `techforge validate-module` quebra no console PowerShell/Windows por encoding cp1252 (glifos do `rich`) | Baixo — não reproduzido em CI (Ubuntu/UTF-8), só afeta experiência local no Windows | Baixa | Corrigir exigiria decidir entre forçar UTF-8 no console ou trocar os glifos do `rich` por ASCII — nenhuma opção óbvia sem trade-off | Se afetar um usuário final, não só desenvolvimento local |
| TD-020 | Packaging | Packaging validation em clean machine 100% real nunca executada — só simulada limpando `%LOCALAPPDATA%\TechForge` numa máquina que ainda tem o repo/`.venv` presentes | Baixo — valida lógica de paths/migrations, não o fluxo de instalação ponta a ponta | Baixa | Testável de verdade só depois de existir instalador (mesma dependência do TD de instalador Windows) | Quando o instalador Windows GUI existir |

**Achados NÃO incluídos nesta tabela por decisão consciente** (infraestrutura pendente, fora do escopo desta consolidação): ausência de instalador Windows GUI, testes de upgrade/failure-recovery que dependem de um fluxo de update formal, e qualquer item condicionado a decisão futura sobre servidor central multi-usuário — todos já registrados em [`docs/limitations.md`](../limitations.md) com essa mesma justificativa.

**Achado descartado por não ser dívida real**: 3 diretórios de módulo órfãos sem manifesto encontrados no ambiente de teste durante a validação do fluxo Desktop — é resíduo do próprio ambiente de desenvolvimento, não um problema de arquitetura.
