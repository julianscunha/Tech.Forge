# TechForge — Fase 18.1
## External Module Sources & Module Declaration

> **Status:** Planejamento / Prompt de implementação
>
> **Objetivo:** Permitir que módulos independentes, desenvolvidos em repositórios externos, sejam adicionados ao TechForge por URL ou arquivo local, apareçam no Marketplace e possam ser instalados, atualizados e gerenciados usando o mesmo pipeline interno.
>
> Esta fase também consolida a declaração formal de:
>
> - tipo do módulo;
> - modo operacional;
> - dependências;
> - compatibilidade;
> - origem;
> - atualização.

---

# 1. Decisão arquitetural

O TechForge suporta duas formas de obter um módulo:

```text
A. Local Package Import
B. External Module URL
```

Ambas devem convergir para a mesma arquitetura:

```text
Module Source
      ↓
Source Resolution
      ↓
Module Metadata
      ↓
Compatibility / Dependency Validation
      ↓
Module Package
      ↓
Trust / Integrity Validation
      ↓
Staging
      ↓
Install Pipeline
      ↓
Registry
      ↓
Runtime
```

O instalador não deve conhecer a origem do módulo.

Ele deve receber um artefato resolvido e validado.

# 3. External modules, not external repositories

A URL adicionada pelo usuário representa:

```text
ONE MODULE
```

Exemplo:

```text
https://github.com/organization/techforge-module-veeam-m365-sizing
```

O TechForge não deve assumir que o repositório contém múltiplos módulos.

Cada repositório externo representa, inicialmente:

```text
Independent Module Project
```

---

# 4. Official module source model

Criar uma abstração oficial:

```text
ModuleSource
```

Responsabilidade:

```text
Resolve module metadata
Resolve module package
Resolve available versions
Check updates
```

Interface conceitual:

```python
class ModuleSource:
    async def inspect(...)
    async def resolve(...)
    async def get_versions(...)
    async def get_update(...)
```

Não colocar regras de instalação nesta abstração.

Recomendação inicial:


---

# 9. Module type

Campo obrigatório:

```yaml
classification:
  type: application | service
```

## Application

Possui interface ou funcionalidade voltada ao usuário.

Pode consumir Service Modules.

## Service

Fornece capacidades reutilizáveis para outros módulos.

Regra:

```text
Service Module
cannot depend on
Application Module
```

---

# 10. Operational mode

Campo obrigatório:

```yaml
classification:
  mode: passive | active
```

Type e Mode são conceitos independentes.

```text
Type
= what the module is

Mode
= how the module operates
```

---

# 11. Passive module

Características:

```text
No mandatory background execution
Loaded on demand
Can execute when requested
```

Exemplos:

```text
Sizing calculator
Report generator
On-demand health check
Data transformation
```

Lifecycle:

```text
Installed
↓
Available
↓
Open / Invoke
↓
Execute
↓
Idle / Unload
```

---

# 12. Active module

Características possíveis:

```text
Background service
Scheduled work
Continuous collection
Persistent integration
```

Lifecycle:

```text
Installed
↓
Validated
↓
Activated
↓
Runtime Start
↓
Running
↓
Background Operation
↓
Shutdown
```

Ativo não significa automaticamente:

```text
Always running forever
```

O Runtime deve controlar o lifecycle.

---

# 13. Valid combinations

Inicialmente permitir:

```text
Application + Passive
Application + Active
Service + Passive
Service + Active
```

Cada combinação possui regras de lifecycle apropriadas.

Não assumir que:

```text
service = active
application = passive
```

---

# 14. Dependency declaration

Todo módulo deve declarar dependências explicitamente.

Estrutura conceitual:

```yaml
dependencies:
  modules:
    - id: com.example.aws-cost-service
      version: ">=1.0.0,<2.0.0"
      required: true
```

Nenhuma dependência implícita.

---

# 15. Dependency rules

Validar:

```text
Exists
Compatible version
Installed
Active when required
Trust compatible
No cycle
```

O Dependency Resolver existente deve ser reutilizado.

Não criar um segundo sistema de dependências.

---

# 16. Dependency direction

Regra principal:

```text
Application
↓ may depend on
Service

Service
✕ may not depend on
Application
```

Service → Service pode ser permitido conforme regras existentes e sem ciclos.

---

# 17. Runtime dependency state

Uma dependência pode possuir estados:

```text

Available
Installed
Inactive
Active
Incompatible
Failed
```

Antes da execução:

```text
Required dependency
↓
Validate state
↓
Resolve
```

O Core deve fornecer mensagens claras.

# 19. Module capabilities

O módulo pode declarar capacidades.

Exemplo:

```yaml
capabilities:
  provides:
    - aws-cost-data
  consumes:
    - aws-pricing-data
```

Capabilities não substituem dependencies.

```text
Dependency
= concrete required module relationship

Capability
= declared functionality
```

# 21. Complete conceptual manifest

```yaml
module:
  id: com.example.veeam-m365-sizing
  name: Veeam M365 Sizing
  version: 1.0.0

classification:
  type: application
  mode: passive

platform:
  min_version: "1.0.0"
  max_version: "1.x"

dependencies:
  modules: []

capabilities:
  provides:
    - veeam-m365-sizing
  consumes: []

runtime:
  entrypoint: backend.main:Module
```

Exemplo Service ativo:

```yaml
module:
  id: com.example.aws-cost-service
  name: AWS Cost Service
  version: 1.0.0

classification:
  type: service
  mode: active

dependencies:
  modules: []

capabilities:
  provides:
    - aws-cost-data

runtime:
  entrypoint: backend.main:ServiceModule
```

A especificação final deve ser alinhada ao manifest existente. Não substituir formatos já implementados sem necessidade.

# 28. Offline behavior

Se o módulo instalado foi obtido por URL e a origem ficar indisponível:

```text
Installed module continues working
```

desde que não dependa da origem em runtime.

Marketplace deve indicar:

```text
Source unavailable
Last successful check
```

---

# 29. Source removal

O usuário pode remover uma URL de fonte.

Isso não deve automaticamente remover o módulo instalado.

Fluxo:

```text
Remove Source
↓
Installed module remains
↓
Update tracking disabled
```

Remoção do módulo é uma ação separada.

# 31. Failure isolation

```text

```

# 32. Development vs production

```text

```

```text
Development install

```

Não permitir que comportamento de desenvolvimento seja usado silenciosamente em produção.

# 42. What not to do

Não:

- criar marketplace federado;
- suportar qualquer URL arbitrária como executável;
- instalar código diretamente de main;
- criar dependency resolver paralelo;
- duplicar installer;
- duplicar update engine;
- criar uma segunda manifest specification;
- misturar Source Registry com Module Registry.

# 43. Critérios de aceitação

A fase estará concluída quando:

1. Importação local continuar funcionando.
2. URL externa puder representar um módulo independente.
3. URL for validada.
4. Metadados forem descobertos.
5. Módulo aparecer como Available.
6. URL não instalar automaticamente.
7. Marketplace mostrar preview.
8. Install Pipeline for o mesmo para ambas origens.
9. Módulo instalado por URL persistir sua origem.
10. Update check funcionar.
11. Update usar pipeline seguro.
12. Módulo continuar funcionando offline após instalado.
13. Remover source não remover módulo.
14. Tipo application/service for declarado.
15. Modo active/passive for declarado.
16. Combinações permitidas forem validadas.
17. Dependências forem declaradas.
18. Resolver existente for reutilizado.
19. Service não depender de Application.
20. Dependências Service→Service seguirem regras existentes.
21. Estado de dependência for considerado no Runtime.
22. Instalação de dependências for assistida.
23. Compatibility for validada.
24. Capabilities forem declaradas separadamente.
25. Segurança for aplicada igualmente.
26. Falha da URL não afetar módulos instalados.
27. Developer workflow externo estiver documentado.
28. Três módulos independentes forem criados em repositórios separados.
29. Nenhum deles exigir alteração do Core.
30. External import acceptance test passar.
31. Update acceptance test passar.
32. Dependency acceptance test passar.
33. Manifest validation passar.
34. CLI e UI reutilizarem os mesmos serviços.
35. AI Context estiver atualizado.
36. Todos os testes passarem.
37. Build passar.

# Regra final

Implementar a capacidade de módulos externos seguindo:

```text
Local File
+
External Module URL
        ↓
Module Source
        ↓
Resolved Module
        ↓
Existing Validation
        ↓
Existing Package Pipeline
        ↓
Existing Dependency Resolver
        ↓
Existing Module Registry
        ↓
Existing Runtime
```

E garantir que todo módulo declare:

```text
What it is
How it operates
What it depends on
What it provides
Which platform versions it supports
```

O resultado esperado:

```text
A developer can build a module in an independent repository,
publish a release,
share only the repository URL,
and a TechForge user can discover, install, update and run it
without modifying the TechForge Core.
```
