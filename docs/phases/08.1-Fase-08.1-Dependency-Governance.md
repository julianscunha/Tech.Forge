# TechForge — Fase 8.1
## Dependency Governance

> **Status:** Prompt de implementação consolidado
>
> **Objetivo:** Implementar a governança formal de dependências entre módulos, com resolução, validação de compatibilidade, detecção de conflitos e ciclos, respeitando as regras arquiteturais entre Application Modules e Service Modules.

---

# 1. Contexto

A Fase 8 implementou o Service Registry.

Agora o TechForge possui uma forma oficial de descobrir capacidades fornecidas por Service Modules.

A próxima necessidade é governar relações entre módulos.

Exemplo:

```text
AWS Cost Service
        ↑
        │ dependency
        │
AWS Sizing Application
```

Um módulo pode depender de outro para funcionar.

Essas relações precisam ser explícitas.

O Core não deve depender de convenções implícitas ou imports privados.

---

# 2. Princípio principal

Toda dependência entre módulos deve ser declarada.

Exemplo conceitual:

```yaml
dependencies:
  - module: aws_cost_service
    version: ">=1.0.0,<2.0.0"
```

Ou, quando a arquitetura preferir capacidade:

```yaml
dependencies:
  - capability: aws.cost.read
    version: ">=1.0.0"
```

A implementação deve definir claramente quando usar:

```text
module dependency
```

e quando usar:

```text
capability dependency
```

Preferência arquitetural:

> Application Modules devem preferir depender de capacidades públicas quando isso reduzir acoplamento.

---

# 3. Regra arquitetural obrigatória

Formalizar:

```text
Service Module
    ✗
    NÃO pode depender de Application Module
```

E:

```text
Application Module
    ✓
    pode depender de Service Module
```

Também permitir, quando fizer sentido:

```text
Application Module
    → Application Module?
```

Esta relação não deve ser assumida automaticamente.

A implementação deve definir uma política explícita.

Preferência:

> Application Modules não devem depender diretamente de outros Application Modules para capacidades reutilizáveis. Capacidades compartilhadas devem ser extraídas para Service Modules.

Se relações Application → Application forem permitidas, devem ser explicitamente justificadas e governadas.

---

# 4. Tipos de dependência

Definir pelo menos:

## Required

Sem a dependência, o módulo não pode funcionar.

```yaml
required: true
```

## Optional

O módulo funciona parcialmente.

```yaml
required: false
```

## Module Dependency

Depende de um módulo específico.

## Capability Dependency

Depende de uma capacidade pública.

Exemplo:

```yaml
dependencies:
  - capability: aws.cost.read
    required: true
```

---

# 5. Dependency model

Criar um modelo interno.

Exemplo conceitual:

```text
Dependency
├── target_type
│   ├── module
│   └── capability
├── target_id
├── version_range
├── required
├── status
└── resolution
```

O modelo deve ser serializável e reutilizável.

---

# 6. Dependency Graph

Criar um grafo de dependências.

Exemplo:

```text
aws_sizing
     │
     ▼
aws_cost_service
     │
     ▼
aws_sdk_service
```

O grafo deve permitir:

- visualizar dependências;
- resolver ordem;
- detectar ciclos;
- identificar módulos bloqueados;
- identificar dependências ausentes.

Não implementar um banco de grafos.

Uma estrutura em memória é suficiente inicialmente.

---

# 7. Resolução

Criar um `DependencyResolver`.

Responsabilidades:

- ler dependências declaradas;
- localizar módulos/capabilities;
- validar versões;
- verificar estado;
- determinar se a dependência está satisfeita;
- produzir resultado estruturado.

Exemplo:

```text
Dependency:
aws.cost.read >=1.0.0

Provider:
aws_cost_service 1.2.0

Result:
SATISFIED
```

---

# 8. Status de dependência

Definir estados claros.

Exemplo:

```text
SATISFIED
MISSING
INCOMPATIBLE_VERSION
DISABLED
CONFLICT
CYCLIC
OPTIONAL_UNAVAILABLE
```

O resultado deve ser explícito.

Não retornar apenas:

```text
true / false
```

---

# 9. Version compatibility

Utilizar versionamento semântico.

Exemplo:

```text
>=1.0.0,<2.0.0
```

Validar:

- versão do módulo;
- versão do serviço/capacidade quando aplicável;
- compatibilidade declarada.

Não implementar um parser próprio se já existir biblioteca confiável disponível no ecossistema Python.

---

# 10. Ordem de ativação

A ativação deve respeitar dependências.

Fluxo:

```text
Dependencies
      ↓
Resolve
      ↓
Activate Providers
      ↓
Activate Consumer
```

Exemplo:

```text
aws_sdk_service
      ↓
aws_cost_service
      ↓
aws_sizing
```

Não ativar um consumidor antes de dependências obrigatórias estarem disponíveis.

---

# 11. Instalação

Durante instalação:

```text
Install requested
      ↓
Read dependencies
      ↓
Resolve
      ↓
All required dependencies available?
      ├── No → BLOCK / INFORM
      └── Yes → Install
```

Nesta fase, não é obrigatório implementar download automático de dependências.

Se estiverem ausentes, o sistema deve informar claramente.

Exemplo:

```text
Cannot activate module.

Missing dependency:
aws.cost.read >=1.0.0

Available provider:
aws_cost_service is not installed.
```

---

# 12. Desativação de Provider

Antes de desativar um módulo, verificar consumidores.

Exemplo:

```text
aws_cost_service
      ↑
      │ required by
      │
aws_sizing
```

Ao tentar:

```text
Deactivate aws_cost_service
```

o sistema deve detectar:

```text
Dependent modules exist.
```

A política deve ser explícita.

Opções possíveis:

1. bloquear desativação;
2. permitir e desativar consumidores automaticamente;
3. permitir com confirmação e marcar consumidores como blocked.

Preferência inicial:

> Bloquear a desativação de um Provider com consumidores ativos que possuam dependência obrigatória.

Evita quebrar módulos silenciosamente.

---

# 13. Remoção de Provider

A mesma regra deve existir para remoção.

Fluxo:

```text
Remove requested
      ↓
Dependents exist?
      ├── Yes → Block removal
      └── No → Remove
```

Não apagar um Service Module que possui consumidores ativos sem avisar.

Se o usuário quiser remover, primeiro deve resolver os consumidores.

---

# 14. Optional dependencies

Dependências opcionais não devem bloquear ativação.

Exemplo:

```yaml
dependencies:
  - capability: aws.cost.forecast
    required: false
```

Se ausente:

```text
OPTIONAL_UNAVAILABLE
```

O módulo continua ativo.

A interface pode informar que funcionalidades específicas estão indisponíveis.

---

# 15. Capability provider selection

Uma capability pode possuir mais de um provider.

Exemplo:

```text
aws.cost.read
```

fornecida por:

```text
aws_cost_service
alternative_aws_service
```

O Resolver não deve escolher silenciosamente.

Política inicial:

- detectar conflito;
- exigir resolução explícita;
- ou utilizar prioridade declarada, se existir uma convenção oficial.

Preferência:

> Nesta fase, priorizar comportamento determinístico e explícito.

---

# 16. Dependency declarations

Integrar a declaração ao manifest oficial.

Exemplo:

```yaml
dependencies:
  - target:
      type: capability
      id: aws.cost.read
    version: ">=1.0.0,<2.0.0"
    required: true
```

A estrutura exata pode ser refinada.

Requisitos:

- tipada;
- validável;
- documentável;
- estável;
- extensível.

---

# 17. Manifest validation

O Module Validator deve verificar:

- estrutura da dependência;
- tipo válido;
- ID válido;
- versão válida;
- regra de tipo de módulo;
- duplicidades.

Exemplo inválido:

```text
Service Module
    ↓
depends on
    ↓
Application Module
```

Resultado:

```text
INVALID_DEPENDENCY_DIRECTION
```

---

# 18. Dependency Governance Engine

Criar um componente central.

Sugestão:

```text
core/backend/app/dependency_engine/
├── models.py
├── parser.py
├── resolver.py
├── graph.py
├── validator.py
└── lifecycle.py
```

Responsabilidades separadas:

```text
Parser
→ interpreta

Validator
→ valida regras

Graph
→ modela relações

Resolver
→ encontra dependências

Lifecycle
→ governa activate/deactivate/remove
```

Não concentrar tudo em uma classe monolítica.

---

# 19. Integração com Module Lifecycle

Integrar Dependency Governance aos fluxos:

```text
Install
Activate
Deactivate
Remove
Update
```

Exemplo:

```text
Activate
    ↓
Dependency Resolver
    ↓
Satisfied?
    ├── No → BLOCKED
    └── Yes → Activate
```

A governança deve ser aplicada no Backend.

O Frontend apenas apresenta o resultado.

---

# 20. Module states

Adicionar um estado derivado quando necessário:

```text
BLOCKED
```

Exemplo:

```text
Module installed
Dependencies missing
Status: BLOCKED
```

Separar:

```text
Disabled
```

de:

```text
Blocked
```

`Disabled` é uma decisão administrativa.

`Blocked` é uma impossibilidade técnica decorrente de dependências.

# 27. Ciclos

Detectar ciclos.

Exemplo:

```text
Module A
   ↓
Module B
   ↓
Module C
   ↓
Module A
```

Resultado:

```text
CYCLIC_DEPENDENCY
```

O ciclo deve impedir ativação quando aplicável.

O relatório deve mostrar o caminho completo.

---

# 28. Atualizações

Antes de atualizar um Provider:

```text
Provider Update
      ↓
Check dependents
      ↓
Compatibility preserved?
      ├── No → BLOCK
      └── Yes → Continue
```

Não quebrar consumidores silenciosamente.

Nesta fase, a implementação pode ser inicial, mas a arquitetura deve estar integrada ao fluxo de update.

---

# 29. Falhas de runtime

Se um Provider ficar indisponível após ativação:

```text
Provider unavailable
      ↓
Dependents evaluated
```

Não é necessário implementar uma cascata automática agressiva.

Inicialmente:

- marcar dependência indisponível;
- atualizar status;
- notificar;
- impedir novas operações que exijam a capability.

# 31. O que não implementar

Não implementar nesta fase:

- download automático de dependências;
- Marketplace remoto;
- resolvedor distribuído;
- múltiplas versões simultâneas;
- execução em containers;
- autenticação;
- permissões.

---

# 32. Critérios de aceitação

A fase estará concluída quando:

1. Dependências puderem ser declaradas oficialmente.
2. Module e capability dependencies forem suportadas.
3. Required e optional forem diferenciadas.
4. A direção Service → Application for bloqueada.
5. Dependências inválidas forem rejeitadas.
6. Version ranges forem validados.
7. Um grafo de dependências existir.
8. Ciclos forem detectados.
9. Conflitos forem reportados.
10. Ordem de ativação respeitar dependências.
11. Consumers não ativarem sem providers obrigatórios.
12. Providers com consumidores ativos não puderem ser desativados silenciosamente.
13. Providers com consumidores ativos não puderem ser removidos silenciosamente.
14. Estado BLOCKED existir quando aplicável.
15. Service Registry for reutilizado.
16. APIs funcionarem.
17. CLI funcionar.
18. Developer Center documentar as regras.
19. AI Context incluir Dependency Governance.
20. Todos os testes passarem.
