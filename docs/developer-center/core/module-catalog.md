# Module Catalog — Fase 11

> Discover, manage, and install modules from multiple sources with integrity verification,
> conflict detection, and progress tracking.

## Overview

The Module Catalog is the distribution layer of TechForge. It aggregates modules from multiple sources
(local repository, official catalog, custom repositories) and enables remote installation with
progress tracking and error recovery.

**Key principles:**
- **Multiple sources, one priority:** LOCAL > OFFICIAL_CATALOG > CUSTOM_CATALOG(s)
- **No partial installs:** Failure returns to clean state; success guarantees consistency
- **Network resilience:** One unavailable source doesn't block others
- **Client-driven installation:** User explicitly clicks "install"; no background polling

---

## Source Types

### Local Repository
- **Location:** `modules/repository/` on disk
- **Format:** `.mod` files (ZIP archives)
- **Discovery:** Filesystem scan on platform startup
- **Use case:** Development, community contributions

### Official Catalog
- **Hosted by:** TechForge (us)
- **URL:** Defined in `CatalogSourceConfig` (typically `https://techforge.io/catalog`)
- **Format:** `index.json` (metada of all modules) + `.mod` files
- **Generated by:** CI/CD pipeline (see "Publishing" below)
- **Use case:** Vetted modules; auto-updates via registry syncs

### Custom Catalog
- **Hosted by:** Third-party (GitHub, GitLab, self-hosted)
- **URL:** User-configured per source in `CatalogSourceConfig`
- **Format:** GitHub Contents API + folder structure (no automation required)
- **Discovery:** Folder `modules/<id>/manifest.yaml` per module
- **Use case:** Organization-specific, user-maintained sources

## Source Configuration

Store in SQLite (`catalog_sources` table):

```python
class CatalogSourceConfig(Base):
    __tablename__ = "catalog_sources"
    
    id: str              # UUID
    name: str            # "My Team Modules"
    url: str             # "https://github.com/myorg/techforge-modules"
    type: str            # "official_catalog" or "custom_catalog"
    enabled: bool        # True/False toggle
    created_at: datetime
    updated_at: datetime
```

**Multiple custom sources are allowed.** No limit; order matters (creation order = priority).

## Official Catalog: `index.json` Format

Published at `https://techforge.io/catalog/index.json`.

```json
{
  "version": "1.0",
  "generated_at": "2026-08-28T10:00:00Z",
  "modules": [
    {
      "id": "module_a",
      "name": "Module A",
      "version": "1.0.0",
      "category": "Utilities",
      "vendor": "TechForge",
      "author": "Team",
      "description": "Does useful things",
      "platform_min_version": "0.5.0",
      "platform_max_version": "999.0.0",
      "checksum": "sha256:abc123...",
      "download_url": "https://techforge.io/catalog/module_a-1.0.0.mod"
    }
  ]
}
```

Generate with:
```bash
techforge catalog build-index <source_dir> --output <catalog_dir>
```

This:
1. Scans `<source_dir>/modules/*/manifest.yaml`
2. Zips each module into `.mod`
3. Writes `index.json` with metada

**No PR/review step:** The `.mod` files are built from source on every merge;
the index is regenerated automatically.

## Custom Catalog: Directory Convention

No automation required. Your repo must have:

```
your-repo/
  modules/
    module_a/
      manifest.yaml
      backend/
        main.py
      frontend/
        main.js
    module_b/
      manifest.yaml
      backend/
      frontend/
```

**That's it.** The platform:
1. Lists `modules/` via GitHub Contents API
2. Reads `manifest.yaml` from each folder
3. On `POST /marketplace/install-remote/{id}`, downloads all files and zips them

No need to pre-build `.mod` files; platform does it on-demand.

## Conflict Detection

When the same `module_id` appears in >1 source, the UI alerts the user:

```
"Available in 3 sources" (chip on card)
```

User chooses which source to install from. **No silent selection.**

Conflict detection is automatic via `detect_conflicts(packages: list[PackageInfo])`.

## Caching

**Per-source, in-memory, with TTL.**

- **Default TTL:** 15 minutes (configurable in `settings.py`)
- **Cache key:** `source_id`
- **Invalidation triggers:**
  - TTL expires → next call fetches
  - User clicks "Refresh" → `force_refresh=True` ignores TTL
  - `CatalogSourceConfig` URL edited → cache cleared immediately
  - Source removed → cache cleared immediately

**Important:** Downloading a module (installing) never uses cache.
`fetch_mod_path()` always fetches from the live source on user click.

## Installation Flow: Remote Source

```
POST /marketplace/install-remote/{module_id}
  ↓
Creates async job: ACQUIRING
  ↓
Resolves provider (which source has this module?)
  ↓
fetch_mod_path() — downloads to cache/
  ↓
Job → VALIDATING → INSTALLING
  ↓
package_manager.install(mod_path) — same pipeline as local
  ↓
Job → DONE (or FAILED with error message)
  ↓
GET /marketplace/install-jobs/{job_id} — polling for progress
```

**No WebSocket/SSE.** Simple polling; UI updates every 500–1000ms.

## Trust & Verification

Remote modules go through the same verification pipeline as local ones:

1. **Integrity** (per-file SHA-256) — generated during install
2. **Signature** (optional, provider-dependent)
3. **Publisher** (resolved from manifest)
4. **Trust Level** (TRUSTED, VERIFIED, UNVERIFIED, MODIFIED, INVALID)

No difference in verification; all modules are modules.

---

## Notifications

The aggregator creates notifications only on availability *transitions*:

- **Source was available, now is not:** "Catálogo indisponível" (warning level)
- **Dedupe:** Only 1 notification per transition; repeated failures don't spam
- **Source recovers:** Optional notification (implementation detail; currently not sent)

## Known Limitations (Fase 11)

1. **CustomCatalogProvider only supports GitHub Contents API.**
   - GitHub, GitLab (with compatible API), other Git hosts with Contents API support.
   - Self-hosted GitLab or Gitea require adapter (Fase 18.1).

2. **No complete rollback on update failure.**
   - If installation partially fails, already-installed files remain.
   - Previous version is NOT automatically restored.
   - Same behavior as local installation (Fase 4 decision, continues here).

3. **No background polling for updates.**
   - "New module available" and "Update available" notifications only appear when
     the user opens the Catalog page.
   - No scheduled background job checking for new modules.
   - Suitable for single-instance/desktop; future phases may add server-side polling.

4. **Favorites are local only (no sync, no rating).**
   - Personal favorite ★ marks; no "4.5 stars from 100 people."
   - No cloud storage or syncing across devices (Central Server phase handles this).

## For Module Authors

### Publishing to Official Catalog

1. Contribute your module to [tech-forge-modules](https://github.com/techforge-org/tech-forge-modules)
   (repo TBD).
2. Submit a PR with your `modules/<id>/` folder.
3. CI builds `.mod` and regenerates `index.json`.
4. Merge → live on next platform sync.

### Publishing to Custom Catalog

1. Create a GitHub repo (or any git host with Contents API).
2. Add `modules/<id>/manifest.yaml` + source files.
3. Configure the URL in TechForge ("Add Custom Source").
4. Your modules appear immediately.
5. No approval step; you control updates and removal.

## Architecture Notes

- **Singleton aggregator:** `CatalogAggregator` instance per platform (shared across requests).
- **Stateless providers:** Each `RepositoryProvider` is stateless; all state (cache, availability tracking) lives in the aggregator.
- **Database session per request:** Notification creation requires DB access; passed through `_fetch_source()`.
- **No hot-reload of provider list:** Changing source config requires next `list_all_available()` call to pick it up (not retroactive).
